Selenium2Playwright Architecture

One LangGraph agent converts TypeScript Selenium to Playwright. The load-bearing idea: the LLM can't lie to the compiler — every conversion passes deterministic validation and a reflection loop before it ships, and everything the agent does is traced, evaluated, and monitored in LangSmith.

Runtime architecture

What happens when someone submits Selenium code — from either client, through the graph, into the observability plane.

The lifecycle wrapped around it

The same system, seen as a process — the Agent Development Lifecycle the repo is built to demonstrate.

Comparing against another architecture?

Five things that separate a system design from a component inventory — judge both diagrams on these.

  1. Is the correction loop first-class? A single “LLM converts code” box hides the mechanism that makes output trustworthy. Look for validate → critique → revise with a bound.
  2. Are the validators deterministic and named? Compiler, typed lint, residue scan — checks the model cannot talk its way past. “QA agent reviews output” is not a gate.
  3. Do evals and monitoring appear in the runtime picture? If observability is missing or bolted on as a footnote, the ADLC story collapses.
  4. Is memory split and grounded? Thread-scoped state vs. cross-thread store, each with a real substrate — not one “memory” cloud.
  5. Is v2 a substrate swap? The graph should move to AgentCore unchanged. If the v2 path requires redrawing the agent, the v1 design is coupled to its host.
